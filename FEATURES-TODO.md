# Features checklist: ask, enrichment, unattended rounds, fleet, arrays

Five features, built one after another. Whoever finishes an item (a person or an agent) ticks its box and
fills in its Notes: what changed, which tests and docs cover it, and anything left out. An item is done only
when the full test suite, `ruff check` and `mypy shellcraft` (199 or fewer) pass.

## Before the features

- [x] **0. `--install-ai` installs an agent and a skill of the same name**
  - Done when: `shellcraft-copilot` and `soc-triage` are installed as an agent and as a skill; a bare name selects both
  - Notes: `ai_install.catalog()` returns a list (it was a dict by name, so the skill replaced the agent); `select` and `needs` work on it. Test: `test_an_agent_and_a_skill_of_the_same_name_are_both_installed` in tests/test_ai_install.py.

## 1. `ask`: the co-pilot inside ShellCraft

- [x] **1.1 `shellcraft/claude_run.py`**: find the client, write the MCP config for this shell, run it headless, stream the text, report cost and session, stop it on cancel
  - Done when: a stand-in client in the tests gets the right arguments and config, its text streams, a cancel kills it, a missing client is one clear line
  - Notes: `Request`, `Result`, `run()` (a generator of text, tool, note and result events), `shell_server()`, `write_config()` (0600, removed after the run). The prompt goes in on stdin, not on the command line (`ps` would show it). The client runs in its own process group; a cancel or closing the generator stops the group. `own_tools` limits the client's built-in tools (`--tools`). Tests: the first part of tests/test_ask_ai.py with a stand-in `claude`.
- [x] **1.2 The `ask` builtin**: `ask QUESTION`, `-b`, `-c`, `--budget`, `--model`, `-n`
  - Done when: the prompt holds the question, the folder and the last command with its redacted output; the answer streams inline; `-b` is a `✦` job that `jobs -k` stops; `-c` continues the last question; free text with `'`, `?` and `#` needs no quotes; it is refused over MCP; `ask_budget` and `ask_model` settings work
  - Notes: `shellcraft/commands/ask_ai.py`; free text is read in `pipeline.run_line` (`ask_ai.free_text`), and the shell skips history expansion and line continuation for it. Different from the plan: (a) `ask` has its own short system text instead of the co-pilot agent's, which tells the AI to open subshells and send alerts; (b) it runs with `--tools ToolSearch`, so the client's own shell and file tools are off and everything goes through the shell (also 3 to 5 times cheaper: about $0.03 a question instead of $0.10); (c) the prompt carries the last five commands, the output of the newest; (d) it works wherever a main shell is reachable, and `-n` without one. String settings `ask_budget` and `ask_model` (`settings.TEXT_SETTINGS`). Tests: tests/test_ask_ai.py (49).
- [x] **1.3 Docs for `ask`**: `docs/ask.md`, `man ask`, help group, walkthrough, getting started, changelog
  - Done when: the docs tests pass and the live check (`ls /nope`, `ask why did that fail`, `ask fix it`, Alt-v) works in a real shell
  - Notes: docs/ask.md (in mkdocs.yml and docs/README.md), `man ask`, the walkthrough's "short way in", getting started, settings page, mcp-and-ai pointer, changelog. `ask` is in the "ShellCraft" group of `help` (there is no "AI and MCP" group there). Live check against the real client in a scratch home: `ls /nope` + `ask why did that fail` streamed an answer (4s, $0.04); `mkdir one/two/three` + `ask fix it` staged `mkdir -p one/two/three` and Alt-v pasted it; a command it ran showed as a `✦ AI` job; `ask -c`, `ask -b` with `jobs N`, piped input and Ctrl-C (status 130, no client left behind) worked.

## 3. Missed alerts are kept, rounds run on their own

- [x] **3.1 Missed alerts**: an alert raised while no shell is open is shown by the next shell
  - Done when: an old spooled alert shows as missed with its age and stays until dismissed; old `sub` and `recording` requests still expire; 200 files and 7 days are the limits
  - Notes: `alerts.drain` posts a plain alert older than five minutes as missed: sticky, with the time it was raised in the text, `disk 97% (missed, 03:12)` or `(missed, Tue 03:12)` on another day. The clock time replaces the plan's "2h ago", because an age would be wrong again a minute after the alert is shown. When more were missed than the three the panel shows, the others wait in `AlertBus.backlog` and move up as you dismiss; a missed alert is never dropped for want of room (an alert of today still is). `alert --list` numbers the waiting ones too and `alert -c [N]` reaches them. The limits are applied when an alert is sent (`_prune`): files older than 7 days go, then the oldest beyond 200. `sub` and `recording` requests older than five minutes are still thrown away. 9 new tests in tests/test_alerts.py.
- [x] **3.2 `shellcraft --watch-rounds PLAN`**: one due round, headless, with a cost cap
  - Done when: nothing due means no client start; a lock stops overlap; `rounds.log` gets one line per run; a failure sends a `warn` alert; `--dry-run` shows the command
  - Notes: `shellcraft/rounds.py`, flags in `cli.py`. It asks `watchplan due` in process, takes a lock (`watchplans/.state/PLAN.lock`), starts the client through `claude_run` as `--agent orchestrator` and writes one line to `rounds.log`. Where it differs from the plan: (a) the agents and the skills they name are handed to the client inline (`--agents FILE`), so a round needs no `--install-ai` (none are installed on this machine); (b) quiet hours do not skip a round, because the plan file means "only crit alerts" by them, and the prompt says so; (c) there is a day budget next to the round budget (`--day-budget`, default 10 USD, 0 for none), since a timer could otherwise spend the round budget 96 times a day; when it is used up there is one `skipped` line and one alert a day; (d) the next round is timed from the start of a round (`watchplan done NAME SECONDS`, a new optional argument) and a round due within 90 s starts, so a 15 minute timer on a 15 minute plan does not skip every second firing; (e) a round is stopped after 30 minutes; (f) the same failure twice in a row is alerted once; (g) the client gets `--tools Agent,ToolSearch`, so a round with nobody there has no Bash, Read or Write. `claude_run.Request` gained `agents`.
- [x] **3.3 `--install-timer` and `--remove-timer`**: a systemd user timer for a plan
  - Done when: the unit files are right, `systemctl --user` is called (a stand-in in the tests), removal cleans up, no systemd prints a crontab line, `--check-analyst` lists the timers
  - Notes: `rounds.install_timer`, `remove_timer`, `status`. The service is `Type=oneshot` and carries `PATH`, `SSH_AUTH_SOCK`, `SHELLCRAFT_HOME` and the `SHELLCRAFT_*` program settings as they were at install time, because a user service starts with a bare environment. The timer is `OnActiveSec=1min` + `OnUnitActiveSec=Nmin`. `SHELLCRAFT_SYSTEMCTL` names a stand-in for the tests. The `loginctl enable-linger` note is printed only when lingering is off. Without systemd a crontab line is printed (every 5 minutes when cron cannot say the interval, since a call with no round due costs nothing). `analyst_setup.launcher()` is the one place that knows how this ShellCraft is started. 19 tests in tests/test_rounds.py.
- [x] **3.4 Docs and the live check**: host analysis page, walkthrough, `man alert`, folder page, changelog
  - Done when: a real capped round on `hugo` ran from the command with the shell closed and its alert showed in the next shell; the timer was installed, listed and removed
  - Notes: Docs: "Rounds on a timer" in docs/ai-host-analysis.md, step 5 of the walkthrough, `watchplans/` and `rounds.log` in the folder page, `man watchplan`, DEVELOPMENT.md, CHANGELOG. Live on 2026-11-12: `--watch-rounds hugo` ran a whole round on `hugo` (orchestrator, host-analyst and ebpf-auditor as sub agents, all through the analyst server) in 76 s for $0.92 and logged it; a second call said `next round in 809 s; nothing started`. `--install-timer hugo` wrote the units, the timer fired after a minute, the service ran under systemd and said `nothing started`, `--check-analyst` listed it, `--remove-timer hugo` removed it. ssh to `hugo` from a systemd user service with the unit's environment works (`systemd-run --user`). Not as written in "Done when": the real round found nothing new, so it sent no alert, and a ShellCraft shell was open at the time. The missed alert was checked with a failing round in a scratch folder (no client): the alert waited in the spool and the bus showed it as `watch round p failed: ... (missed, 10:25)`. At $0.92 a round, a round every 15 minutes uses up the default day budget in under three hours; the docs say so and suggest `--every 120`.

## 4. The fleet view, reports, hostscan rules

- [x] **4.1 `report` module**: `report save UNIT --status ... --summary ...`, `report list`, `report show`
  - Done when: a status record is always written, a Markdown report only when something was found or a body is given, old reports are removed, the body is redacted
  - Notes: `modules/report.py` over `shellcraft/fleet.py`. Layout: `fleet/host/web01.json` and `reports/host/web01/20261112-165320-warn.md` (UTC time and status in the name, so `report list` reads no file). 0700 folders, 0600 files, 30 days, 200 reports per unit, 256 KB per body. `report list` is also the status listing. 25 tests in `tests/test_report.py`
- [x] **4.2 `fleet` builtin**: every host and device in one table, `fleet UNIT` for the detail, `--json`
  - Done when: hosts, aggregator devices, last round, `LATE` and `never`, changed counts and open findings show from a scratch home in the tests; it pipes as plain text
  - Notes: `shellcraft/commands/fleet.py`. Order: crit, warn, late, never, ok. `LATE` is a record older than twice the plan's interval (the shorter one when a unit is in two plans). A finding counts by the tag `host:NAME`, the bare name, or `kind = host` with that value. A bare name means the host when a device has the same name. It only reads and creates no folder. 12 tests in `tests/test_fleet.py`
- [x] **4.3 hostscan rules for the eight integrity checks**: `pkg-verify`, `suid`, `capabilities`, `ld-preload`, `units`, `sudoers-files`, `sshd-config`, `shell-rc`
  - Done when: every rule has a case and a clean sample in `tests/test_hostscan.py` and its id in `man hostscan`; `sshrun H suid | hostscan suid` works through the fake ssh
  - Notes: eight subcommands and 17 rules (46 in all), each with a bad case, a clean sample and its id in `man hostscan`; every flag carries `path=` for `known_paths`. Live on a real host: six checks end in `no flags`, `capabilities` gives a note where `getcap` is not installed, and the one flag raised was a true one. Known limits: `apk verify` prints nothing without arguments, so `pkg-verify` has no data on Alpine (a fix for `sshrun`); `pkg-verify` without sudo cannot read most files (a note counts them); a unit that runs a relative path after `cd /tmp` is not seen; cloud images flag the cloud-init sudoers line and Raspberry Pi OS its shipped preload (quiet both with `known_paths`)
- [x] **4.4 AI side and docs**: `report` in the analyst tools, the round skills end with `report save`, the alert carries the report path, the `host:NAME` tag, `docs/fleet.md`, changelog, `AI-TODO.md` item 5
  - Done when: one live round on `hugo` leaves a status in `fleet`, and Alt-v on its alert pastes the report path
  - Notes: `report` is an analyst tool and never cached; the three analysts and the `watch-rounds` skill end each unit with `report save`, tag findings `host:NAME` or `device:AGG/NAME`, and put the report path into the alert's `content`. Live: one round on `hugo` (ok, 63 s, $0.85) left `host:hugo ok` in `fleet` with its seven checks and three findings. Not seen live: the round was quiet, so it wrote no report and sent no alert. The path in the alert is covered by the tests of `report save` and the alert's `content`, not by a real alert yet
